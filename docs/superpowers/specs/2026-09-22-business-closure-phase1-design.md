# 第一阶段：设备/BOM 绑定、统一库存与旧入口收口

日期：2026-09-22  
状态：用户已在后续回复“请继续”确认进入实施计划；功能未实施、未部署、未迁移数据。  
范围依据：用户认可分三阶段补齐业务闭环，本阶段仅落实第一阶段四项规则。

## 1. 目标、边界与选择

目标：研发、计划、采购、仓库及订单人员使用可追溯的产品和库存依据。新业务不能错配设备/BOM，不能用不明确的库存证明可交付，不能通过旧接口绕过仓库办理流程。

采用方案：保留现有页面与业务服务，补充必要的关联/版本记录，复用已有库存限制计算。未选择整套重构，也不建立新的通用工作流、独立库存账或消息总线。

本阶段交付：

1. 设备归属确认、BOM 发布版本及生产计划引用校验。
2. 物料库、库存管理、订单库存校验、普通/正式齐套的基础库存口径统一。
3. 旧库存写入口停用，有效办理入口仍使用现有权限和事务。
4. 历史数据待核对状态、人工确认入口、不可覆盖的历史依据。

不在本阶段：采购完成口径调整、自动补采、已有计划的工程变更执行、订单交付数量回写、客户退货、多工序半成品、自动排产、财务模块。不得以本阶段完成宣称四模块全链路已闭环。

## 3. 设备与 BOM：身份、发布和使用

### 3.1 身份与存储

- 现有 BOM 设备根节点 ID 作为设备 BOM 的稳定身份；`productLine` 保留为展示/兼容字段，不再作为唯一的业务关联依据。
- 为设备根节点增加可空的产品根节点关联，引用现有 `ProcTaskTreeNode` 根节点。服务端保证关联对象为根节点，不能绑定其他设备下的子系统。
- 一个产品根可以包含多个设备型号；一个设备 BOM 只能归属于一个产品根。
- 首次绑定需有权限人员选择并填写核对依据。无论名称是否相同，均不自动建立历史归属。
- 一旦发布过版本，设备归属不可直接更换；错误归属须停用原设备并建立正确设备，原计划和版本保留。有关联版本的根节点/产品根禁止物理删除。
- 新增 `ProcBomRevision` 保存设备根 ID、产品根 ID、递增版本号、完整结构和有效用料快照、指纹、发布人、发布时间、发布依据及停用信息。设备内版本号唯一，外键删除使用 Restrict。
- 当前 `ProcBomNode` 树继续作为可编辑工作稿；不新增另一套草稿编辑器。已发布快照不可修改或删除，修改工作稿只能发布新版本。

### 3.2 发布规则

发布前必须同时满足：已确认设备归属；至少一条有效物料；所有物料来自物料库；ERP 编码、实际单位、正数用量完整；无循环/跨设备结构；无未解决的重复编码或单位冲突。

同编码、同单位、不同装配位置可以按明确规则汇总用量，同时保留结构来源行；同编码不同单位禁止发布。不用默认“件”补齐真实缺失单位，不把模糊名称匹配作为正式物料来源。

提交携带工作稿版本指纹及请求 ID；发布事务内重读结构和物料身份、验证归属、生成快照和审计。并发编辑导致指纹变化时返回冲突，禁止发布混合版本；同一请求重试不产生新版本。

权限：现有 `material:import` 继续用于编辑；新增 `bom:publish` 用于归属确认、发布和停用，并要求 BOM 可访问页面权限。新权限不自动授予普通角色，管理员可通过现有权限管理分配。发布人直接记录登录身份，不能取前端自由文本。

### 3.3 新业务使用

- 创建正式生产计划先选产品，再选该产品下设备及已发布、未停用版本。前端筛选与后端校验同时存在。
- 请求携带设备 ID、版本 ID；客户端不能提交任意用料覆盖该版本。保存版本 ID、产品归属、完整快照与指纹，沿用现有计划历史和幂等机制。
- 防重复按“产品＋设备＋月份”校验；更换版本不能绕过本月已有计划校验。兼容已核对旧计划，不仅检查新格式记录。
- 发布新版不自动替换任何现有计划。停用版本只禁止新计划引用，历史计划保持原依据并标示版本停用；后续变更办理属于第二阶段。
- 普通齐套可看工作稿，但明确显示“草稿试算，非生产执行依据”；正式计划齐套必须读取该计划冻结的版本。新建备货/采购需求不得从未发布工作稿直接生成。
- BOM 维护、导入、普通齐套快捷编辑等所有写入口只改工作稿；批量替换不得删除已发布版本依赖的设备身份，失败时整次回滚。

### 3.4 旧计划

无版本 ID 的旧计划保留原 BOM 快照，标记“历史执行依据待核对”，不填造 V1。

有权限人员可对历史计划的产品、设备及原快照建立独立核对记录，记录原指纹、确认人、时间和依据。核对不替换快照、不推定等同当前版本；指纹或归属发生变化后原核对失效。

未核对计划可查看历史、继续已派发作业的签收、报工、检验和必要退料，但禁止新增/扩大派工及扩大目标。保留有实物业务的历史办理能力，不能因资料治理把质量或退料流程锁死。

## 4. 统一库存：共用基础量，不混淆业务范围

### 4.1 唯一基础口径

复用 `warehouseStockExposure`、`pendingWarehouseIssues` 及现有 ERP 核对规则，抽出一个共享库存读取/计算服务。共享服务仅依赖 Prisma 和现有纯计算模块，不依赖采购或订单业务服务，避免模块循环依赖；不创建额外库存余额表。

基础身份是 ERP 存货编码＋仓库＋单位。查询必须明确仓库范围及物料编码，不通过拉取第一页库存结果做全量校验。

基础数量定义：

```text
账面现存量 = ERP 库存快照现存量
基础业务可用量 = ERP 可用量
               − 尚未被 ERP 覆盖的发料
               − 尚未被 ERP 覆盖的本地冻结/报废限制
               − 尚未被 ERP 覆盖的盘亏扣减
```

ERP 可用量已排除的占用不再次扣减；发料和签收是同一业务不同阶段，不能各扣一次。凭证确认与后续 ERP 快照的覆盖关系沿用现有规则，同一来源事实只计一次。

本地收货、良品退料、盘盈在未完成 ERP 覆盖前单列为待同步数量，不直接增加基础业务可用量。待检、不良不能作为合格可用量。

缺少快照、单位不一致、来源冲突或扣减后不合理为负时，返回 `unknown` 和原因，可用量为 null；不得用 0 冒充已确认缺货，也不得通过截断成 0 掩盖账务冲突。

### 4.2 消费方的合法差异

| 消费方 | 使用规则 |
|---|---|
| 物料库、库存管理 | 相同仓库范围下使用相同基础现存量和业务可用量，显示范围与同步信息 |
| 普通 BOM 齐套 | 按所选设备/版本和明确量产仓范围计算；使用共享基础可用量 |
| 正式计划齐套 | 在共享基础量上处理其他计划占用、本计划分配、已确认未耗用线边及采购在途；原有扣减迁移后不得重复扣 |
| 订单库存校验 | 使用已映射物料和明确可出货仓库范围；显示即时库存参考，不宣称已预留或保证可交付 |

不同仓库范围、计划占用和 BOM 版本产生的数字不同是合法差异，页面必须说明差异来源。统一不意味着成品订单直接使用原材料数量，未建立成品编码映射的设备订单为待核对。

每次读取返回查询时间、相关分仓快照时间、限制明细及问题列表；聚合不以最新一个仓库的时间冒充所有仓库均已同步。服务读取过程中使用一致的数据视图，正式写入前重验关键来源版本。

### 4.3 订单物料映射与核对

- 订单明细保留原始名称、SKU、单位与识别结果，另存确认后的 `materialId`、核对人、时间、依据及来源指纹；映射变更写审计。
- 精确 ERP 编码命中且单位一致才可作为明确映射；不同客户 SKU、模糊名称只提供候选，必须人工确认。
- 手动确认需要订单页面权限及新增 `order-processing:material-map` 动作权限。不能自动沿用上次同名商品匹配；本阶段只做逐明细确认，不新增通用别名管理。
- 原 SKU、单位、确认物料的 ERP 编码或有效性变化使核对失效。单位不一致时禁止比较数量，本阶段不做自动换算。
- 无映射、无有效快照、单位异常显示“待核对＋原因”，不读旧库存或历史订单 `stockQty` 兜底。
- 新识别、订单详情、检查刷新和相关导出共用新读取口径；历史保存的库存数仅作为历史快照显示。GET 不回写库存、订单状态或初始化旧演示数据。
- 本阶段不更改发票生成/导出流程，不把“库存待核对”擅自变成财务单据禁止生成；明确库存参考与财务单据状态互不代替。

## 5. 旧入口与权限收口

停用旧 `order-processing` 下的 `inventory/stock-in`、`inventory/:itemId/stock-out`、`inventory/:itemId/adjust` 写入。移除前端遗留调用/按钮；服务方法也不能继续改旧账，避免内部调用绕过路由。

兼容期旧路由对已登录请求返回 410 和去仓库工作台办理的提示，不先执行旧初始化、识别入库或任何数据库写入；未登录仍由全局认证拒绝。不自动重定向或重放旧 POST 到新业务，因为其单据字段和语义并不等价。

旧库存 GET/详情/导出调用迁移到统一读取并校验现有库存页面权限；旧识别入库流程不再提供“确认入库”，仅识别能力有真实消费者时可保留无写入解析。旧订单采购导入不在本阶段悄悄改成 ERP 正式订单写入。

有效仓库发料、入库、退料、盘点入口保留原始单据关联、后台动作权限、真实操作人、版本冲突与幂等控制。本阶段不改变财务发起盘点的已约定边界、不自动扩大普通角色权限。

旧库存表与历史流水保留只读，不合并其余额进 ERP。未知外部消费者通过 410 明确暴露，不能为兼容而继续写旧账。

## 6. 界面与历史治理闭环

不新增独立驾驶舱或复杂数据治理模块。使用现有 BOM、计划、订单页面：

| 问题 | 去哪里处理 | 谁可以处理 | 完成条件 |
|---|---|---|---|
| 设备未绑定产品 / BOM 未发布 | BOM 页面顶部状态与确认/发布动作 | 有 BOM 发布权限人员 | 有明确根节点关联及有效发布版本 |
| 历史计划依据未核对 | 计划详情依据区 | 有计划办理与 BOM 发布权限人员 | 原快照指纹核对记录有效；不改原用料 |
| 订单明细未匹配物料 | 原订单明细行核对动作 | 有订单物料核对权限人员 | 物料、ERP 编码、单位均明确 |
| 库存来源缺失或冲突 | 原库存详情和仓库工作台的相关原单 | 现有仓库/ERP 核对权限人员 | 来源问题解决并重新读取通过 |

每项待核对须显示具体原因、处理入口与可办理角色。无权用户只读且显示需联系哪类经办人员；不得显示无效果按钮或一键“全部确认”。已有待办聚合可链接这些状态，不另建重复审批单。

无根节点/多根节点的历史型号不能擅自选一个为设备身份，须人工整理工作稿。确认前保留原树展示和原始来源，禁止正式发布/新计划使用。

## 7. 验收矩阵

| 编号 | 场景 | 必须结果 |
|---|---|---|
| B1 | 产品 A 提交设备 B 或其版本 | 后端拒绝，无计划/领料副作用 |
| B2 | 未绑定、草稿、停用版本或不存在版本用于新计划 | 拒绝并说明处理入口 |
| B3 | 发布后编辑工作稿或发布新版 | 已有版本和计划快照不变 |
| B4 | 并发编辑与发布、重复发布请求 | 冲突或同一结果，不产生混合/重复版本 |
| B5 | 引用版本的设备根删除或批量替换 | 拒绝破坏性删除，原数据完整 |
| B6 | 历史计划核对及扩大派工 | 未核对不扩大；原已执行业务可收尾；核对不覆盖快照 |
| I1 | 同编码、仓库范围、单位、数据版本跨页面读取 | 基础量一致，计划衍生量差异可解释 |
| I2 | 发料后签收、冻结、盘亏，随后 ERP 核对同步 | 每个事实只扣一次，覆盖后不重复扣减 |
| I3 | 未同步收货、待检、不良、良品退料、盘盈 | 不提前增加合格可用量 |
| I4 | 无快照、不同单位、无物料映射、负数冲突 | 显示未知/待核对，不伪装成 0 或库存充足 |
| I5 | 普通齐套与正式计划齐套 | 共享基础量；正式计划保留占用、线边和在途规则 |
| O1 | 模糊名称命中或同名不同规格 | 仅候选，不自动通过库存校验 |
| O2 | 订单来源、物料编码或单位变更 | 原映射失效并重新核对 |
| O3 | 订单刷新、详情、导出以及历史发票 | 新库存参考一致，历史财务内容不被重写 |
| P1 | 普通登录账号直接调用旧库存写接口 | 不写库、不执行初始化；已停用响应明确 |
| P2 | 无权限调用新绑定/发布/核对动作 | 403；有权限也不能伪造操作人或跳过来源校验 |
| P3 | 新请求重复提交、版本冲突和事务失败 | 不重复生成记录，失败无半完成副作用 |

验证分层：现有隔离测试回归；新增上述业务模型/服务/路由权限测试；前端类型及 API 构建；实际渲染和关键交互（桌面与窄屏、普通角色、空态/冲突/无权限）。数据库约束和并发在明确隔离的测试数据库验证，禁止借用线上库。

最终真实 ERP 验收必须包含实物来源、凭证核对、后续同步和跨页面读数对照。未做真实联调不能标记“上线业务闭环已验证”。

## 8. 实施顺序、迁移和回退

1. 先建立必要的新增字段/版本表及单测，兼容旧记录；没有已确认归属时仅显示待核对。迁移脚本可准备，真实数据库执行另行确认环境与备份。
2. 完成 BOM 核对/发布、计划引用与历史计划核对路径，随后启用新计划强校验，避免只加拦截不提供解决入口。
3. 抽取共享库存读取，在同一批固定测试数据上逐消费者对照；先保持各自仓库范围，不擅改量产仓或成品仓定义。
4. 完成订单明细映射和统一校验，收口旧读写入口；普通角色和重复请求验收通过后才视为本阶段代码完成。

上线前保留数据库备份和原始单据；未知历史记录不自动补为“已核对”。新增关联、发布或映射的历史补齐均由授权业务人员办理，本次开发不批量写入用户业务数据。

失败时回退本阶段应用改动、保留新增只读记录与审计，禁止删除历史来恢复。代码回退不得重新开放旧库存写漏洞：需保留停用补丁或服务端阻断。已经形成新版本引用的业务不能交给不认识该引用的旧版本继续写入，恢复兼容前暂停受影响的新建/扩大动作，历史查询和安全收尾保持可用。

项目当前存在大量未提交修改。实施前逐文件核对已有变更，不整体覆盖、不清理工作区。本设计不授权提交、创建 PR、部署、执行生产迁移或修改真实库存。
