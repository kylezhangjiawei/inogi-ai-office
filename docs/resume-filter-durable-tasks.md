# 简历二次筛选：持久任务与分批评分

原故障是 80 人的二次评分请求在上游 60 秒超时。仅把 HTTP 改成异步或延长超时，不能解决人数增长、进程重启和整轮重做的问题。本次让提交、模型处理、进度查询和最终发布分开运行。

## 处理与容量边界

- 默认冻结提交时整个岗位范围，不再静默截断 80 人。单轮最多 5,000 人；超限明确拒绝并要求缩小岗位范围。5,000 是保护上限，不是实测吞吐承诺。
- 先根据岗位、人数和指令分析统一规则，不把全体简历塞入意图分析。每次评分最多 8 人，同时限制候选人输入总字符数。全局前 N 名在所有评分完成后统一计算。
- 多个 API 实例共用 PostgreSQL 队列，全局最多两个二次筛选任务，每任务最多两批并行，正常最多四个二次评分调用。初筛、聊天等其他场景不在这个并发限制内。
- 每批验证候选人完整且不重复后，保存模型结果及进度。失败后点击「继续执行」使用原任务和原始候选人快照，只补做尚未成功保存的批次；「继续查询」只查状态，不提交新评分。
- 评分阶段使用独立的严格 JSON Schema，`action` 只能是 `filter`，候选人 ID 限定为当前批次；不再复用允许追问的分析格式。模型明确拒绝结构化输出参数时沿用网关的兼容处理，返回后仍须通过业务校验。[千问结构化输出说明](https://help.aliyun.com/zh/model-studio/qwen-structured-output)明确区分 JSON Object 与结构约束，前者不能保证字段名和类型。
- 收到不符合评分协议的模型结果时，仅对该未完成批次最多再纠正两次；始终使用同一候选人快照、统一规则和批次编号，每次重查权限及执行权。纠正不增加并发，不能补造分数、遗漏候选人或把追问当作成功。网关异常与数据库保存失败不会进入格式纠正循环。持续错误保留成功断点，完整版本仍不发布。
- 格式错误日志记录批次序号、错误分类、模型和网关请求 ID，不记录简历或模型回复正文。纠正成功后，该批次断点汇总本次纠正过程的模型用量；整个尝试失败前的用量仍可在网关调用记录中查询。
- 模型调用在数据库事务外。评分全部就绪后，按每 100 人一条批量写入，在一个事务中发布完整版本和任务完成状态。中途数据库写入失败会整体回滚，评分断点仍可复用。
- 完成任务保留概要，清除冗余简历快照、分析和批次断点；正式评分历史保留。失败任务保留断点供继续执行，目前不自动清理失败任务。
- 历史版本列表按数据库完整计数返回最近 50 个版本，每版本只读取一份说明，避免按 1,000 条评分行截断统计。

## 恢复与授权

每个账号同时只能有一个进行中任务，相同请求重复提交会复用该任务。查询和重试按当前登录账号隔离。开始执行、每次模型调用前和发布前均重新检查账号、角色权限及权限目录停用状态。

任务租约为 120 秒，每 20 秒续期。服务停止会取消本地调用；进程异常退出后，其他实例在租约过期后接管。所有断点和发布操作验证当前执行令牌及数据库实时时钟，旧实例不能写入。连续三次进程接管仍中断时显示失败，可人工续跑。

页面刷新或重新进入后从服务端恢复任务。查询没有整轮 15 分钟截止；单次查询最多等待 20 秒，网络故障按 3/6/12 秒退避，连续四次失败后显示「继续查询」。切换账号、岗位或版本时，旧响应不会覆盖当前对话。已发到供应商的请求在取消后仍可能产生费用；模型已返回但断点尚未保存就崩溃的小窗口可能重做该批次，不能承诺上游计费恰好一次。

## 发布顺序

1. 在发布环境备份数据库，应用 `20260910120000_candidate_filter_durable_tasks` 迁移，生成匹配 Prisma Client。
2. 发布匹配的 API 和前端。旧 `/candidate-filter-sessions/iterate` 也改为返回 HTTP 202 的任务信息，不能继续用同步结果协议；当前页面使用 `/iterate/async`。
3. 用真实模型先验证少量候选人，再验证整个目标岗位。确认人数完整、进度增长、刷新恢复、失败续跑和最终版本统计；同时观察上游成功率和实际费用。

首次切换应避开旧版本仍在运行的内存任务：这类任务没有数据库断点，不能迁移。后续改变评分快照或分批协议前应等待旧任务结束，或实现协议版本迁移，不能直接用新分批算法解释旧批次下标。回退 API/前端时保留新增任务表，不删除断点；旧程序不会处理新队列中的任务。

## 已验证范围

自动测试使用匿名候选人、模拟模型响应和专门的本机 PostgreSQL 测试库，不读取业务数据库，也不向真实模型发送简历：

- 500 人分批评分，中途模型超时后保留 24 人成功结果，换实例只完成剩余批次。
- 101 人任务从已保存的 8 人断点跨实例恢复，后续批次格式错误自动纠正；500 人任务的多个批次分别注入缺字段、追问、错误数组等异常，验证只发布完整且唯一的评分版本。持续错误验证有限停止、保留成功批次及人工继续执行。
- 真实本机 HTTP 端点经过 OpenAI SDK、适配器和网关，验证 101 人完整评分、严格格式参数、旧模型仅报告 `json_schema` 不支持时的兼容处理，以及回退后仍不合格时不得保存。非格式 400、403、超时和网关空回复不进入业务格式纠正；这是传输协议验证，不是真实供应商验收。
- 评分完成后第一批 SQL 写入故障，正式评分全部回滚；再次续跑不调用模型而成功发布 500 人唯一版本。
- 多实例争抢、同账号去重、越权查询、租约过期和锁等待、旧进程拒写、权限停用、完整性校验及部署取消。
- 75,200 条历史评分、55 个版本，包含单轮 5,000 人，验证最近 50 个完整版本的计数和岗位范围。
- 前端查询恢复、有限网络退避、长任务等待、登录刷新卡住时的超时、账号/岗位/版本切换及多轮历史边界。

本地验证不代表供应商不会再超时，也不代表线上已修复。真实供应商耗时、线上数据库性能和浏览器完整操作仍需发布后验收。

测试数据库必须通过 `CANDIDATE_FILTER_TEST_DATABASE_URL` 显式指定，且仅允许本机 `resume_filter_test`。PostgreSQL 用例未设置该变量时跳过，不能把跳过计为持久化验证通过。
