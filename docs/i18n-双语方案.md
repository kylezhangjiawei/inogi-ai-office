# 中英文双语（i18n）实施方案

> 状态：**方案已定，未实施**（2026-07-08 讨论定稿）。
> 范围：先做中美协同模块，验证机制后按同一套字典体系渐进铺开到其他模块。

## 一、现状与工作量结论

- 项目**没有任何 i18n 基础设施**：无翻译框架，全部文案硬编码中文，散在 JSX、常量表、toast、确认弹窗中；
- 协同页面与研发侧**共用组件**（RDTaskManagementPage / RDMyWorkspacePage 等）——文案抽一次 key，两侧同时 i18n-ready；
- 协同模块相关静态文案估算 **600~900 条**；
- **协同模块完整双语约 7~12 个工作日**；全站双语为数周级，不一次做。

### 文案分四类（难度递增）

| 类型 | 例子 | 处理方式 |
|---|---|---|
| ① 静态 UI | 按钮/标题/空态/占位符 | 字典 + `t(key)`，量最大但机械 |
| ② 模板插值 | 「移交任务给 {name}」 | 字典模板 + 变量插值（**不需要 AI**） |
| ③ AI 生成内容 | 日报汇总、任务小结 | **不是翻译**——prompt 加输出语言，模型原生写英文 |
| ④ 用户/历史内容 | 留痕正文、历史审计记录、通知 | 不翻；可选「翻译」按钮按需 AI 翻译 + 缓存 |

## 二、分期计划

```
P0   i18n 层：t() + 服务端字典(systemSetting KV) + 用户语言偏好 + 顶栏切换器
     （缺 key 回退中文，永不白屏）                                    1~2 天
P1   文案 key 化（工时大头：JSX 硬编码中文 → t(key)，按页面分批）
     → AI 初翻 → AI UX-Writer 角色校对 → 入库                        3~5 天
P1.5 翻译管理页（见下）                                              含在 P1
P2   AI 内容跟随用户语言（日报/小结 prompt 一行改动，感知最强、成本最低）
     + 通知模板双语 + Word 过程报告英文版                             2~3 天
P3   打磨：日期/数字本地化（toLocaleDateString 传 locale）
     + 可选：留痕正文「翻译」按钮（系统内模型按需翻译+缓存）           1~2 天
```

## 三、关键设计决策

### 1. 语言切换粒度：按用户（不按模块路由）

中方支持人员（如结构/电子工程师）也用协同模块，按路由强制英文会伤到他们。
**用户偏好存个人设置**：美国成员设英文后登录全协同模块即英文，中方看中文，同一页面各看各的。

### 2. 字典存数据库，不打包进前端

- 字典存 `systemSetting` KV（如 `i18n.en` 键），前端 `t()` 启动拉一次并缓存；
- **翻译管理页改完即时生效**（刷新即见），不需要重新构建发版；
- 提供导出/导入 JSON，进 git 留版本。

### 3. 翻译管理页（自建轻量版 Crowdin）

- 三列表：中文原文 / 英文 / 所属页面；
- 搜索 + 按模块过滤 + **行内编辑** + 状态标记（AI 初翻 / 已人工校准）；
- 单条「AI 重翻」按钮 + 全量导出/导入；
- 权限：超管/协同管理员；放系统管理分组。

### 4. AI 翻译 + AI 校对（基本免人工）

- **不买第三方翻译服务**：传统 MT（DeepL/Google/Azure）对 UI 短文案缺上下文、术语必然打架；
  项目已有 AI 模型管理（qwen/openai 通道），900 条文案 <5 万 token，成本几分钱；
- 两轮不同视角：
  - 初翻 prompt：带术语表 + 界面上下文标注（「这是按钮，≤3 个词」）批量出 JSON 字典；
  - 校对 prompt：换角色「英文 SaaS 产品 UX Writer」逐条查术语一致性/母语语感/按钮长度，可换模型交叉校；
- 兜底：真实使用中发现别扭 → 翻译管理页随手改；
- **唯一建议人工的**：30~50 词核心术语表（工作项/留痕/主责人/驾驶舱…）由中方或美方花五分钟扫一遍后冻结。

（若将来仍想接第三方 API 参考排名：DeepL 质量第一 ~$25/百万字符；Azure 性价比第一，免费 200 万字符/月；Google $20/百万；腾讯/百度便宜但英文地道性弱。Crowdin/Lokalise 等翻译平台对本团队规模过重，不推荐。）

### 5. 历史数据不翻（已确认的取舍）

审计记录 comment、已有通知、已生成日报存的是中文文本——只能「从上线日起新内容双语」。
彻底方案（结构化存储+显示层渲染）是大手术，不做。

## 四、风险与预期管理

1. **工时大头在 key 化不在翻译**：上万行 JSX 里逐处替换 `t()`，按页面分批、每批构建+走查；
2. 新功能开发从此要写 key 而非硬编码中文（缺英文时回退中文，不阻塞开发）；
3. 后端下发文案（如 status_label）改为前端按枚举本地化；
4. 术语表先冻结再批量翻，否则 AI 各处不一致。
