- 状态：待确认（含 3 项待定，见第八节）
- 日期：2026-08-06
- 范围：研发任务驾驶舱、我的工作台

---

## 一、需求来源

领导原话：

> 我本意并不是做一个总的，而是每个人同一类目（如：分子筛）自己搞自己的，但是之前所有跟这个相关的合并在他自己名下的一个总的表中，而不是根据每日时间而分散；同时关联的总的只有管理员能看到，比如小裴的分子筛部分与小朱的分子筛部分。

补充确认（本轮沟通结论）：

1. 「分散」指的是**任务过于分散**，不是进展留痕、也不是每日汇报。
2. 「表」指的是**任务表按分类的数据表**。
3. 分组用类目 ID，但界面显示类目名称。
4. 管理员范围：**主管算，组长不算**。
5. 实现走**视图聚合**，不做数据层的真合并。

## 三、概念定义

三个「表」必须区分清楚，避免与领导反对的「一个总的」混淆。

| 名称 | 主键 | 内容 | 可见范围 | 现状 |
| --- | --- | --- | --- | --- |
| **成员类目表** | 成员 × 一级类目<br>（如「小裴 / 分子筛」） | 该成员在该类目下的全部任务，汇成一张数据表 | 本人 + 管理员 | 新增 |
| **任务** | 任务 ID | 成员类目表中的一行 | 沿用现有可见性 | 已有 |
| **类目汇总表** | 一级类目<br>（如「分子筛」） | 该类目下各成员的成员类目表，分节并列 | **仅管理员** | 新增 |

关键点：**主体是成员类目表**。小裴的分子筛与小朱的分子筛是两张互不合并的独立表，各自归属本人。类目汇总表只是管理员的观察视角，不产生任何归属关系的改变。

## 四、功能需求

### FR-1 成员类目表

- 每位成员在每个一级类目下，拥有且仅拥有一张表。
- 表归属于该成员本人，标题体现「成员 + 类目」。
- 该成员在此类目下的任务，全部作为表中的行呈现，不再以独立卡片形式散落。
- 日期作为表中的一列（截止日期等），不作为拆分表或分组的依据。

### FR-2 分组键与显示

- 分组键：分类树节点的 `category.id`（一级类目）。
- 键的取得方式：聚合时从分类树结构位置逐层带下来，**不新增任务字段、不迁移历史数据**。
- 界面显示：类目名称 `category.name`，不暴露 ID。
- 类目改名后分组保持稳定；任务被移动到其他类目时，自动进入新类目对应的表。

### FR-3 表格内容

行 = 任务（含子任务展开为行，保留层级标识）。

列（**待确认，见第八节**）：

| 列 | 数据来源 |
| --- | --- |
| 任务标题 | `title` |
| 状态 | `status` / `status_label` |
| 进度 | `progress` |
| 截止日期 | `due_date` |
| 最新进展摘要 | `latest_progress_summary`（现成） |
| 附件数 | 现有附件计数 |
| 协作人 | `collaborators` |

### FR-4 类目汇总表（管理员）

- 结构：一级类目 → 成员分节 → 该成员的成员类目表。
- 例：「分子筛」下并列展示「小裴的分子筛」与「小朱的分子筛」两张表。
- 管理员可横向对比同一类目下不同成员的推进情况。
- 非管理员访问不到此视图，也无法通过接口取到他人数据。

### FR-5 数据口径

与个人工作台保持同源（`readMergedTaskCategories`），即：

- **跨产品库聚合**：一个人的任务是其在所有产品库任务的并集，不被「当前产品库」切分。
- **包含已完成任务**：成员可回看自己完成的任务。
- **排除已归档任务**。
- **子任务展开为行**，保留其在任务树中的层级关系。

## 五、权限规则

| 角色 | 判定依据 | 自己的成员类目表 | 他人的成员类目表 | 类目汇总表 |
| --- | --- | --- | --- | --- |
| 普通研发成员 | `page:rd-my-workspace` | 可见 | 不可见 | 不可见 |
| 组长 | `rd-task:override-priority`（目录描述：组长及以上） | 可见 | 不可见 | **不可见** |
| 主管 | `rd-task:reassign`（即 `hasFullAccess`） | 可见 | 可见 | 可见 |
| 超管 | `*` | 可见 | 可见 | 可见 |

- 汇总表的权限闸口为 `hasFullAccess`（`*` 或 `rd-task:reassign`），**不使用** `canReadAll`。
- 因此持有 `rd-task:view-all`（跨部门只读查看全部留痕）的角色也看不到汇总表 —— 此为满足「组长不算管理员」的必然结果，**待确认（见第八节）**。
- 权限校验在服务端接口层完成，前端隐藏入口不作为安全手段。

## 六、实现约束

以下约束用于防止实现走偏，属于需求的一部分。

1. **只做视图聚合**：底层任务、进展留痕、附件一条不动。聚合结果为只读视图。
2. **禁止复用 `applyTaskMerge`**：该方法会改主责人、归档源任务、AI 重写描述，会破坏各任务独立的截止日期、完成评分与审批状态（这些是绩效考核的输入）。
3. **不需要数据迁移**：分组键从结构位置推导。
4. **可逆**：视图逻辑变更不影响已有数据，出错不产生脏数据。
5. 不引入新的审批流程；成员日常记录不受聚合逻辑阻塞。

## 七、明确不做

| 不做 | 原因 |
| --- | --- |
| 不改每日汇报（`listDailyReports`） | 日报是给管理层看当日情况的独立产物，按天生成是其固有形态；领导所指的「分散」不在此 |
| 不改任务合并审批流 | 与本需求语义相反，保持原样 |
| 协同工作台（us-collab）不提供此视图 | 协同任务的 `category_path` 恒为空、无分类归属，与现有「项目文件夹」在协同下隐藏的处理保持一致 |
| 不做跨成员的合并记录 | 领导明确反对「做一个总的」 |
| 不改任务的创建方式 | 本需求解决呈现问题，不限制成员如何建任务 |

## 九、验收标准

- [ ] 成员在我的工作台进入某一类目，看到的是一张包含该类目下全部本人任务的数据表，而非多条独立任务卡片。
- [ ] 同一成员同一类目下只有一张表；任务不再按日期被拆成多条呈现。
- [ ] 类目改名后，成员类目表的分组不发生漂移，且表头显示新名称。
- [ ] 任务被移动到其他类目后，自动出现在新类目对应的表中。
- [ ] 子任务在表中作为行出现，且可辨认其层级归属。
- [ ] 已归档任务不出现在表中；已完成任务出现在表中。
- [ ] 同一成员在不同产品库下的同类目任务，合并在同一张表中。
- [ ] 主管可进入类目汇总表，看到同一类目下各成员分节并列的表。
- [ ] 组长、普通成员访问汇总表接口被服务端拒绝。
- [ ] 聚合前后，任务的主责人、截止日期、完成评分、审批状态均无变化。
- [ ] 协同工作台下不出现此视图。
