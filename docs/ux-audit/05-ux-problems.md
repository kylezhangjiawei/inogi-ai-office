# 05 · 信息架构与任务体验问题

审计日期：2026-09-17。本报告只做产品诊断与结构建议；没有修改代码、菜单、权限或视觉样式。问题来自当前源码与文档对照，不是线上用户访谈或可用性测试结论。

## 优先判断

优先改善用户能否识别“在哪办、办的是什么对象、结果是否真实、谁接下一步”，随后再讨论入口数量。不要先把所有驾驶舱合成一个大驾驶舱，也不要因为同一个代码目录而把生产归入采购。

优先级定义：P1=影响核心任务可达性/结果信任，应先验证和处理；P2=增加查找/理解/交接成本，应在结构梳理阶段处理；P3=低频或规模扩大后再处理。以下“影响”是设计推断，不是已测到的故障率。

## 哪些应该合并

“合并”首先指产品对象与入口归属，未授权删除页面或迁移数据。

| 候选 | 决策 | 合并后的主职责与保留项 |
| --- | --- | --- |
| 报关 AI + 报关处理 | **强合并候选** | 一个单证批次工作区；上传/识别、差异复核、模板生成是阶段；保留文件对比详情 |
| 研发问题分流 + 问题 AI | **业务整合候选** | 一个问题库，队列分流与分析详情不同视图；先定义来源与状态迁移，不能把演示记录直接当正式问题 |
| 字典邮箱 + 邮箱管理 + 各业务连接入口 | **唯一配置源候选** | 同一连接目录，业务模块选已授权连接；不同历史数据先验证映射，不做无依据自动合并 |
| 旧检验放行/批记录/追溯演示与正式生产执行 | **按对象统一权威入口** | 正式检验、放行、批次档案作为主线；旧示例保留在演示区，不复制真实原单 |
| 采购订单/库存 + 供应链分组 | **导航归位，不合并页面** | 订单是交易对象、库存是 SKU/仓库视角、物料是主数据；三者各有独立任务 |
| 研发/协同/采购操作留痕 | **已完成，不重复提改造** | 当前统一 /audit-log，保留模块筛选和历史链接 |
| 研发及部门知识库 | **入口聚合已完成** | 当前库切换已可用，继续保留权限/密级与专业能力；协同库单独入口是否整合待验证 |

不建议直接合并：研发与中美协同任务池、员工档案与用户账号、报价与采购订单、理论齐套与按期齐套、知识库与质量受控文件、AI 成本与采用反馈、设计 ECO 与制造 ECN。它们可能共用导航域和对象关联，但业务责任不同。

## Tab / Drawer / Modal / 独立页面决策表

| 场景 | 建议承载 | 理由与约束 |
| --- | --- | --- |

| 订单行承诺/履约/收货历史 | Drawer | 必须可见原行身份和数量单位；深层操作避免连续嵌套多层弹窗 |

| 新建问题 | 当前两步 Drawer 可保留 | 输入→相似查找存在顺序；进入分析后转完整问题详情 |
| 外部版本差异复核 | 独立资料/版本工作面 + 文件预览 | 两文件证据和大量差异需持续上下文；归档最后确认用 Modal |
| 员工胸牌编辑、长报销编辑 | 独立编辑面/有稳定身份的表单 | 耗时长、字段多、需要草稿恢复；简单字段补录仍可 Modal |
| 改负责人、补录原因、删除/回退/发布确认 | Modal | 单个明确动作、简短字段；说明影响和目标对象，避免笼统“确定” |
| 我的岗位任务 vs 团队管理 | 独立角色入口或同页明确范围切换 | 个人待办与团队分派不应让用户猜；后端范围不能只靠前端切换 |
| 质量规则、协议、连接参数 | 设置域内 Tab/子页 | 同配置域但有独立保存发布；保留发布版本、未保存提示 |

## 功能层级过深的具体路径

| 当前可观察路径 | 多余理解成本 | 建议 |
| --- | --- | --- |
| 供应链驾驶舱 → 备货计划 → 计划展开 → 采购批次 → 订单详情 → 行级日期/履约 Drawer | 需要记住同一需求在多种对象间的关系 | 稳定计划详情、订单行面包屑/回链；保留现在已有筛选和返回恢复 |
| 物料库 → 更多管理 → T+ 集成 → 连接/同步配置 | 用户必须先知道技术连接属于物料页 | 平台连接目录可发现，业务页保留便捷状态与同步 |
| 研发工作台 → 任务操作弹层 → 子 Tab → 转采购/样品等表单 → 最终确认 | 弹层中再次启动长任务，责任与对象层级复杂 | 快速动作保留；长流程用稳定工作面；父任务 ID 和当前操作始终可见 |
| 生产执行 → 选择计划 → 现场/转产/放行 Tab → 目标批次/作业 → 操作表单 | 岗位入口不直接、Tab 刷新定位不稳 | 从本人队列直达作业/批次；明确原计划并可返回 |
| 知识库 → 更多操作 → RAG 回填/文件名修复 | 管理性维护混入内容浏览；不是普通用户高频操作 | 放入知识库管理；普通成员不需要看到技术维护入口 |

“层级深”不是指所有路径都必须减到两次点击。要减少的是反复定位同一对象和不必要的层间切换，保留必要的核对、独立批准与版本证据。

## 本阶段不应给出的结论

- 不声称这些问题已导致具体转化率或效率损失；尚无行为数据。
- 不声称所有用户都看到 75 个菜单项；真实可见性取决于权限、导航隐藏和部署配置。
- 不把同名函数/文件视为重复产品，也不把共享 API 前缀当作部门组织结构。
- 不把预览里的工单、数量、通知与审批当作正式数据。
- 不把缺少公开独立页等同于没有功能；样品、备货、质检、档案等已存在深层入口。
- 不重新建议已经做好的保护：采购返回上下文、统一审计、知识库聚合、样品轮次区分、转采购本机草稿、履约独立批准均应保留。
